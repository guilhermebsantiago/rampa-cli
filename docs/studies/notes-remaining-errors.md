# The judgments' remaining weak spots: 1.1.1 in another language, 2.4.4 on ACT 5effbb, and the link-mismatch pairs

Three weak spots were left by the [1.1.1 dev fixes](notes-111-dev-fixes.md) and the [2.4.4/2.4.6 change](notes-244-246.md): two true short Portuguese alternatives that 1.1.1 still called wrong on the fresh-page study's dev pages, the recall of 0.50 on ACT rule 5effbb (Link in context is descriptive), and the corrupted pairs whose links were pointed somewhere else (`link-mismatch`), told apart 0 times out of 10. These notes find the cause of each, change the prompt or the facts a finding rests on, and measure the change on the W3C ACT test cases, the corrupted pairs and the dev pages of the [fresh-page study](real-pages-2026-10-fresh.md).

**In short.**

- **1.1.1.** The prompt asked for the model's description of the image "in one short English sentence", while it asked for the suggested alternative in the image's language. On a Portuguese page, Rampa's word checks, which drop a "describes something the image does not show" claim when the model's own answer keeps naming the alternative's words, could only meet the suggestion, and the model's suggestions for "Capa da edição 751" and "Boletim InfoGripe" dropped some of them. The description is now asked in the same language as the suggestion (1.1.1 version 5): the language declared for the image, its element's `lang` or else the page's, which Rampa takes to be the alternative's. The check reads the description and the suggestion together; a name or a number, such as "InfoGripe" or "751", reads the same in any language, so it still meets an English description. On the dev pages, the two false positives were dropped in both runs of the new prompt, by the check that already read the suggestion alone: the new prompt's suggestions kept every word of the alternative ("Capa do Jornal da Unicamp, edição 751, …", "… dados do Boletim InfoGripe"). The new check on the description dropped no claim on the dev pages or the ACT cases; only tests back it. Three runs of the old prompt reported "Capa da edição 751" every time and "Boletim InfoGripe" twice. The 7 true positives were reported in every run, and precision at the default threshold was 0.88 and 0.78 with the new prompt against 0.70, 0.70 and 0.64\* with the old one (\*one false positive labelled by a Claude agent here, not by the study; on the study's labels alone that run is 0.70 too); the runs vary because the model's reading of a few images does (it took a photo of Lula for one of Jair Bolsonaro in one run of each prompt). On the ACT test cases and pairs of 1.1.1 nothing changed: every set stays at precision and recall 1.00, and verification drops no claim.
- **2.4.4, ACT 5effbb.** The three failed examples missed were not a candidate or a model problem: the model failed all six, with the right problem. The fact rule turned three of them into suggestions, because "HTML", "EPUB", "Plain text", "Download" and "Workshop" are not on the generic lists. A new fact grounds two of them: a link text that names only a file's format (Failed Example 5's "HTML", "EPUB", "Plain text") with nothing in its programmatically determined context that could say which document: no sentence or list item of its own, no heading above it, no header cell; or one that names only its download ("Download", Failed Example 6) in a table row whose header cells do not name the row's subject, which sits in a data cell beside it; and in neither case in the site's menus, header or footer. Recall on 5effbb went from 0.50 to 0.83 with precision 1.00; "Workshop", whose description sits in another paragraph, stays a suggestion, because only the model's reading of a specific word could make it a finding, and that reading is what was wrong on real pages. Nothing else changed on the ACT sets. On the 1,367 link candidates of the dev pages, the new fact holds for none, and a judgment of the dev pages before and after the change gives the same 2 findings and 15 suggestions, item by item.
- **`link-mismatch` pairs.** The fact the brief proposed, a destination page whose title or main heading shares no meaningful word with a specific link text, does not hold up: on the dev pages it holds for 5 of the 376 links whose destination was read and tells it apart, and none of the 5 is a mismatch ("Report a problem with this page" leads to "Feedback", "Right of withdrawal" to "Terms and conditions"). A title is a summary of a page. A link to a part of this page can be read further: Rampa reads that part, and for a heading the section it opens, and when the page names the part (a word of its id is a word of its text, as `#hours` and "Opening hours: Monday to Friday") while the link's text and context name none of it, the text may promise something else. That fact now grounds a `mismatch`, except for links that name a region or a control rather than a subject (skip links, "back to top", a carousel's arrows, a link to a menu, a search field or a form). It rests on shared words, so a synonym or a translation of the part's name ("Contato" for "Fale conosco") still satisfies it, and then only the model's verdict decides. The pairs went from 0 to 9 of 10 told apart, and on the dev pages it holds for none of the 32 links to a part of the page (31 skip links and an audio player's link). Neither number is a held-out measure: the fact was written after reading the corruption, which points every link to such a part, so the pairs now measure this fact as much as the model; and its guards were written after reading the 32 dev links. Its precision on real pages is not measured.

**After review.** A review of this change (2026-10-23) found that both 2.4.4 facts held on real-page shapes they were not written for, and narrowed them. The file-kind fact now reads every landmark around a link, not only the closest (a `<section>` in the site's header is still the header), takes a number without a unit as naming a document ("2024 (PDF)"), and reads a "Download" with no format only in a table row. The same-page fact now reads a heading's section rather than its name alone, leaves out skip links, "back to top", a carousel's arrows, replies such as "Sim", links to a region, a control or a form field and links whose capitals the part's initials spell ("FAQ"); and a repeated id is read at its first element, as a browser goes to it. On the data of these notes nothing changed: the facts hold for the same links (none of the dev pages' 1,367), the dev judgment gives the same 2 findings and 15 suggestions, and the 102 ACT and pair answers score the same; a fresh run of the model with the final code, the demo's recorded evaluation, gives the same numbers too (below). The review's guards were written from hand-built page shapes and the dev pages' links, so they are no held-out measure either.

**Only the allowed data was used, and the numbers are optimistic.** The fixes were chosen from the W3C ACT test cases, the corrupted pairs and the fresh-page study's dev split, and they are measured on the same data. A held-out measurement has to come from round 3 or a later round of real pages; the round-3 study under way was not read, used or waited for.

## Data and scope

- **Used:** the W3C ACT test cases (`rampa eval`, ACT `a9a1483e`) of 1.1.1 and 2.4.4, with their corrupted pairs; the fresh-page study's **dev split only**: the twelve dev pages' recordings (24 files, all matching the SHA-256 in `study/fresh-2026-10-11/data/recordings.json`) and judgment caches, copied from the study's backup, and their labels, read only from rows of `data/findings.json` whose `split` is `dev` (`study/fresh-2026-10-11/scripts/dump_fp.py dev`, and this work's `study/notes-remaining/list111.py`, which filters the same way).
- **Not used:** the fresh-page study's test split (no page, recording, label or finding of it was read), the first real-page study's data (its dev findings are cited from [notes-244-246.md](notes-244-246.md), not read again), and the round-3 pages, labels and runs (`study/round-3-*`).
- **Labels:** the study's two Claude judges, a pre-annotation and not ground truth (see the study's caveats). Nothing was relabelled. The two 1.1.1 findings no study label covers, which runs that asked the model again newly reported (an accurate alternative read against a headline painted over its picture, and a hidden image below the default threshold), were labelled by one Claude agent, here, both false positives, and are said so where they appear.
- **Model:** Gemma 4 12B through a local Ollama, temperature 0, one judgment per candidate, on a GPU other jobs used at the same time. Under that load, the same prompt does not always give the same answer, so the runs that ask the model again were repeated.

## 1. 1.1.1: an alternative in Portuguese, a description in English

### What was wrong

The two false positives left by the 1.1.1 dev fixes, with the model's answer in the study's run (version 4):

| Page | Alternative | What the judges said | `imageShows` | `suggestedAlt` |
| --- | --- | --- | --- | --- |
| unicamp.br | "Capa da edição 751" | the cover of the newspaper's edition 751, "ED. 751" printed on it | "The front cover of Jornal da Unicamp featuring a portrait of Orides Fontela and headlines about various topics." | "Capa do Jornal da Unicamp com a foto de Orides Fontela e manchetes sobre diversos temas." |
| fiocruz.br | "Boletim InfoGripe" | the InfoGripe bulletin's cover graphic, a map of Brazil with the InfoGripe logo | "A map of Brazil divided into regions with different colors and the InfoGripe logo." | "Mapa do Brasil com regiões coloridas e o logotipo do InfoGripe" |

Both claims were "describes something the image does not show". Verification already drops that claim when the suggestion keeps every word the alternative names: "Lula" in "Lula com um selo de 16%". Here the suggestions dropped "edição 751" and "Boletim", and the description, which named "front cover" and "InfoGripe", was in English, so no word of a Portuguese alternative could ever meet it. The prompt asked for the two fields in two languages: the description "in one short English sentence", the suggestion "in the requested language", the language of the image's element or page.

### What was tried

- **The new rule alone, on the study's answers.** Reading the description and the suggestion together, with the study's English descriptions, removes nothing: replayed offline from the study's cache, the dev findings are the same 13 (7 true positives, 3 false positives, 3 uncertain). "Boletim" is no word of an English sentence.
- **Text drawn in the image, from OCR.** A language-independent check would compare the alternative with the words drawn in the picture. Rampa's OCR (tesseract.js, used by 1.4.5) read "Orides" and "Fon" on the 350 × 514 cover and nothing on the 173 × 116 bulletin graphic, the "Tour 360º" image or the "Ceará em Destaque" photo: not enough to rest a fact on. It was left out.
- **The description in the alternative's language.** Asked for both fields in Portuguese, in two quick trials on the two images, the model kept answering "fail", but its suggestion kept the alternative's words three times out of four: "Mapa do Brasil com estados coloridos indicando dados do Boletim InfoGripe" twice, and once "Capa do Jornal da Unicamp, edição 751, com a manchete…". With the old prompt, asked once the same way, it kept them for one of the two (InfoGripe): the model's answers vary from run to run, which is why the full runs below were repeated. This is the change made.

### The change

1. **The prompt (1.1.1 version 5).** `imageShows` is written in the requested language, as `suggestedAlt` already was: "Describe what the image shows in imageShows, in one short sentence in the requested language, the language of the text alternative", and the user prompt says "Write imageShows and suggestedAlt in: Brazilian Portuguese (pt-BR)". The requested language is the one declared for the image (its element's `lang`, else the page's), which the prompt calls the alternative's; on a page that declares the wrong language (a 3.1.1 failure), the two differ, the description comes in the declared language, and the check can meet only names and numbers, as before. On an English page nothing is asked differently than before, but the wording changed, so every 1.1.1 judgment is asked again once. The question about images hidden from assistive technology (`hidden-images.ts`) was not changed.
2. **Verification.** A "describes something the image does not show" claim is dropped when every word the alternative names (left out: the kind of picture, such as "logo", "foto", "imagem", and short function words) is in the model's description and suggestion taken together, with the reason "the model's description of the image keeps every word of the current alternative". The check that reads the suggestion alone stays first. Words are compared as written, so a name or a number ("InfoGripe", "751") meets the description in any language, and a Portuguese word meets only Portuguese. As the earlier facts, it never speaks for an alternative the placeholder pattern or the generic-word list flags, and it applies only to the "describes something the image does not show" claim, never to "leaves out what the image conveys", since "Chart" can rightly become "Chart of sales by quarter".

## 2. 2.4.4: recall 0.50 on ACT 5effbb

### Which failed examples were missed, and why

ACT 5effbb has six failed examples. In the demo's recorded evaluation as it was before this change (`demo/recorded/eval/ollama-gemma4-12b`, recorded 2026-10-16) and again here, every one had a candidate, the model judged every one, and the model answered "fail" with the problem "generic" on all six. The three counted as passed were the fact rule's: their fail is reported as a suggestion, because the text is not on the generic lists.

| Failed example | Link | Its programmatically determined context | Before |
| --- | --- | --- | --- |
| 1 | "More" to `#desc` | none | finding (generic list) |
| 2 | "More", `div role="link"` | none | finding (generic list) |
| 3 | "Go", an SVG link | none | finding (generic list) |
| 4 | "Workshop", alone in its paragraph; the workshop is described in the paragraph before | none | suggestion |
| 5 | "HTML", "EPUB", "Plain text" in a list; the book's title "Ulysses" is a bold paragraph above it, not a heading or a list item the list is nested in | none | suggestions |
| 6 | "Download" in a table cell; "Ulysses" and "1.61MB" are data cells of its row, under the header "Books" | the header cell "Books" | suggestion |

So the misses were neither candidate selection nor the model: the fact rule turned three right answers into suggestions. The passed examples next to them are the same texts with a context that names the book: the formats in a list nested under the list item "Ulysses" (Passed Example 5), the formats under a header cell "Ulysses" (Passed Example 6), "Download Ulysses in HTML" (Passed Example 8).

### The facts added

A fail with the problem "generic" is also a finding when:

- **the text names only what kind of file it gets, never which document** (`kindOnlyLinkText`, generic-text.ts): it is made only of a format ("HTML", "EPUB", "Plain text", "PDF", "DOCX", "MP3"…), the act of getting a file ("Download", "Baixar", "Descargar"), a size and filler ("PDF (2 MB)", "Versão em PDF"). A size has a unit: a number without one, a year or an edition ("2024 (PDF)", "751 PDF"), says which document. Like "Click here", such a text names no document; unlike it, it says what kind of thing happens, so it was not on the generic list;
- **and nothing in its programmatically determined context could say which** (`kindOnlyUncompleted`, link-purpose.ts): no sentence, paragraph, list item or cell text of its own, no description, no heading anywhere above it; it is not in the site's navigation, header or footer landmarks, at any depth, nor an item of a menu, a list of links that do not all name a file's kind; and either it names a format and has no header cells, or it sits in a table row whose header cells do not name what the rest of its row does: a data cell beside it holds a name, the table gives that row no row header, and no header cell names it (`rowSubjectOf`). This is technique F63, context in content that is not the link's programmatically determined context. A "Download" with no format is read only in such a row: elsewhere it names an action or a site's download page, which only the model's reading could tell apart.

Failed Examples 5 and 6 are this fact; Passed Examples 5, 6 and 8 are not (their list item, header cell or sentence names the book). The menu and landmark guards are for real pages: debian.org's "Download", in its menu next to "About Debian" and "News", was a false positive in the first real-page study, and a format can also be a site's section ("HTML" in MDN's menu). The landmark guard reads every landmark around the link, not only the closest: the collector reads every `<section>` as a region, so a "Download" in a `<section>` of the site's `<header>` has the region as its closest landmark.

**Not added: the model's reading of a link with nothing around it.** Failed Example 4's "Workshop" has no context at all, and only a reading of the word says it is not enough. A rule "any 'generic' claim on a link with no context, no heading above, no landmark and no menu" would catch it. On the dev pages such links are rare (24 links with no context outside a landmark, 5 of them outside a menu too, all skip links), and the model, asked about each of them with the unchanged prompt, passed every one. It was still left out: the rule would rest a finding on the model's reading of a specific word alone, which is the reading the fact rule stopped trusting after it was wrong on real pages ("ISTs", "TOC", "Download"). A word that names a thing ("Workshop", "Tables") cannot be told from one that names a destination without that reading.

## 3. The link-mismatch pairs: a fact that grounds a mismatch

The `link-mismatch` corruption points every named link of a passed example to `#hours` and adds a paragraph `<p id="hours">Opening hours: Monday to Friday, nine to five.</p>`. The model said "mismatch" on 9 of the 10 corrupted pages (the tenth, an SVG link labelled "Go to the main content.", it passed); since the 2.4.4/2.4.6 change every mismatch was a suggestion, because no checked fact supported it.

### The fact the brief proposed, measured: another page's title

"The destination page's title or main heading shares no meaningful word with the link text, when the text is specific." Measured on the dev pages, with the link's sentence, heading and description counted as what it promises, words of three letters or more without accents, a word and its longer forms counted as one ("language", "languages"), and the destination's title, heading, description and address path as what it is: of the 376 links whose destination was read and has a title that tells it apart (not the site's name, not shared by other addresses, not a not-found page), 5 have a specific text that shares no word with it, and none of the 5 is a mismatch:

| Link text | Destination's title |
| --- | --- |
| "Data for GDP" | "Gross Domestic Product: Quarter on Quarter growth: CVM SA %" |
| "Yes I found this page useful" | "Thank you" |
| "No I didn't find this page useful" | "Feedback" |
| "Report a problem with this page" | "Feedback" |
| "Right of withdrawal" | "Terms and conditions" (the page holds it) |

The first real-page study found the same on its own dev pages ([notes-244-246.md](notes-244-246.md): 28 of 410 shared no word, home pages, skip links, language switchers, and a privacy notice that holds the "Declaração de Cookies" its link names). A title summarizes a page; an abbreviation, a reply, or a broader page that holds what the text names share no word with it and are no mismatch. So a mismatch with another page stays the model's suggestion.

### A fact on a part of this page

When a link points to a part of this page, Rampa reads that part: its text, or for a heading the section it opens, its name and what follows up to the next heading of its level or higher. That is more than a title, which summarizes a page, but it is still words: the fact rests on shared words, not on what they mean. The fact (`namesNoPartOf`, link-purpose.ts) holds when:

- the page names the part: a word of its id is a word of its text (`#hours` and "Opening hours…"; `#configuration` and the heading "Configuration"), the site's own name aside (its host's labels and its title's words: fiocruz.br's `#block-portal-fiocruz-views-…` and "A Fiocruz tem 16 unidades" share only the site's name), and words that name how a page is built aside ("block", "view", "wrapper", "main", "content", "skip", "menu", "nav", "footer", "search", "carousel", and their Portuguese and Spanish forms such as "conteudo", "principal", "rodape", "busca", "navegacao");
- the part names no region or control: it is no landmark (main, navigation, banner, contentinfo, search, a form, a region), no control or form field (a button, a link, a search field, a menu), not inside the site's navigation, header or footer, its search or a form, and it holds no landmark and no form field (a wrapper around the menu, a search box, a feedback form). A skip link names the region it jumps to, not its subject;
- the link's text does not move within the page or answer a widget: not a skip link ("Skip to…", "Ir para…", "Pular para…", "Go to…"), "Back to top", "Voltar", a carousel's "Próximo" or "Anterior", a permalink, "Sim" or "Não";
- the link's text is neither generic, an address, nor a number (a footnote's "1"), and no word of it in capitals is spelled by the initials of the heading's name or of the id's words ("FAQ" and "Frequently asked questions", "GDP" and `#gross-domestic-product`);
- and no word of the link's text, its context, its heading, its header cells or its description is one of the part's words or the id's, read loosely: two words that begin with the same four letters count as one, so "Specifications" names `#specs`.

A table of contents entry that points to another section fails this way, and so do the corrupted pairs. What the fact cannot tell apart is a synonym or a translation: "Contato" for a heading "Fale conosco", "Dúvidas" for "Perguntas frequentes", "Opening hours" for a part in Portuguese, "critics" for a section "Reception" that never says "critics". For those it holds, and only the model's verdict decides whether a finding is reported; in one run of Gemma 4 12B during the review, on two hand-built pages of such links ("GDP", "the options below", "critics", "FAQ", "Contato", "Sim", "Não"), the model passed all of them, so this is a risk measured on no real page, not an observed false positive.

On the dev pages it holds for none of the 32 links to a part of the page. 31 are skip links, to the content, a menu, the search field, the footer or past a carousel, and one opens an audio player ("Listen 42:22"); 7 lead to a landmark, 18 to a part with no text of its own (an empty anchor, a search field, a carousel's skip button), and 7 to a part whose id and text share no word (an id made only of words for how the page is built, such as `#main-content`, a plugin's name, or a name for the region rather than for what it holds, as `#navegacaoPrincipal` over the menu's items). That is no held-out number: the site-name and id-word guards were written after reading these 32 links (without the site-name guard, fiocruz.br's "Ir para Área de Destaque" would hold), and so were the guards a review of this change added (below). The only dev evidence of how the model reads a link to a part of the page is a wrong one: on berkeley.edu, the model called "Skip to main menu", which leads to the menu's first button, "About", a mismatch. It stayed a suggestion because the button's id, `#main-menu-item-1`, shares no word with "About"; with an id such as `#about`, the fact as first written would have made it a finding. The review's guards leave it out whatever the id.

### What the pairs measure now

0 of 10 told apart before, 9 of 10 after, with the same answers. The corruption makes every link point to a part whose id and text name it, `<p id="hours">Opening hours: …</p>`, and this fact was written after reading it, so the pairs now measure this fact as much as the model, as the `link-generic` pairs measure the "follow me" word rule since the 2.4.4/2.4.6 change. They are not a held-out measure, and they say nothing of the fact's precision on real pages, which is not measured: it never fired on the dev pages. A mis-pointed link with a numbered id (`#section-3`) never satisfies the fact, since digits and "section" are no names.

## Limits

- **Tuned on what it is measured on.** The facts and the prompt were chosen by reading the dev pages' false positives, the ACT failed examples and the corrupted pairs, and they are measured on the same pages, so these numbers are optimistic, an upper bound. The same goes for the guards the review added, written after reading the dev pages' same-page links and hand-built page shapes. A held-out measurement has to come from round 3 or a later round.
- **Small numbers, and noise.** 10 decided 1.1.1 dev findings before this change (7 true and 3 false positives); the change removes 2 false positives, while a repeated run of either prompt adds or removes another one or two. Two or three runs of each prompt cannot give a stable precision, and the intervals overlap. 5effbb has 6 failed examples, and the link-mismatch pairs are 10 pages of one corruption.
- **The model reads faces and words, sometimes wrong.** The new prompt did not change the model's verdict on the two images: it still says "fail", and the fix rests on its suggestion keeping the alternative's words. A model that drops them again, or names another person, is reported as before.
- **The 2.4.4 facts are narrow on purpose.** They fire where the page leaves a link without a context that names its document, which is the shape of the ACT examples and rare on real pages: on the dev pages, never. A format link under a heading that does not name its document, a "Download" in a menu, and a "Download" with no format outside a table row stay the model's suggestions. "Workshop" (Failed Example 4) is missed.
- **The same-page fact reads words.** A synonym, a translation or an abbreviation the part never spells out satisfies it, and then only the model's verdict stands between a fine link and a finding. Its precision on real pages is not measured.
- **Hand-written lists.** The formats and download words cover English, Portuguese and Spanish; the words that name how a page is built, in ids, are a short list.
- **Labels from Claude agents,** the study's two judges and, for two findings, this one: a pre-annotation that needs human review.

## Reproduction

From the repository root, after `pnpm build`, with the dev pages' recordings and caches copied from the study's backup into `study/fresh-2026-10-11/pages/<slug>/` (kept out of git; check them against `data/recordings.json`). The "before" CLI is a build of `d23cfb5` (`git worktree add`, `pnpm build`, and its `dist/cli.mjs`).

- **1.1.1, the study's answers:** `bash study/notes-remaining/run.sh dev <label> 1.1.1 <cli> --offline` replays each page's study cache, which only the version-4 prompt reads.
- **1.1.1, asking again:** `bash study/notes-remaining/run.sh dev <label> 1.1.1 <cli> --fresh-cache`, once per run, with the "before" CLI for version 4 and this branch's for version 5; then `bash study/notes-remaining/run.sh list111 <label>` lists a run's findings with the study's dev labels and its precision at the default threshold.
- **2.4.4 on the dev pages:** `bash study/notes-remaining/run.sh facts244` computes the facts of every candidate with no model; `bash study/notes-remaining/run.sh dev before 2.4.4 <before cli> --fresh-cache` asks the model; `bash study/notes-remaining/run.sh copy-cache before after` and `bash study/notes-remaining/run.sh dev after 2.4.4 dist/cli.mjs --offline` score the same answers with this branch; `bash study/notes-remaining/run.sh list244 before after` compares them item by item.
- **ACT and pairs:** `bash study/notes-remaining/run.sh act <criteria> <cache> [cli] [--offline]` runs `rampa eval` on those criteria and their pairs. For 2.4.4, `act 2.4.4 <cache> <before cli>` asked the model and `act 2.4.4 <cache> dist/cli.mjs --offline` scored the same answers; for 1.1.1 each version asked its own (`act 1.1.1 <cache> <before cli>`, then `act 1.1.1 <cache>`). A run in which w3.org pages fail to load says so at its end ("page(s) with errors") and was run again.
- **The demo:** `pnpm exec vitest run --dir test test/demo-replay.test.ts` replays the six recorded pages from `demo/recorded/cache` and fails on any miss.
- **Not scripted:** the OCR trial on the two images (section 1) and the two quick trials of the prompt in Portuguese were one-off observations; no committed script rebuilds them.
- Run outputs and caches go to `.rampa/`, which is kept out of git. The model runs here: Gemma 4 12B through Ollama, on 2026-10-23.
